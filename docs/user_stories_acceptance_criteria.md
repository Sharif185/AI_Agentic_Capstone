# User Stories and Acceptance Criteria

University Student-Support Case Agent — BSE4104 Capstone, Week 1

## User Story Acceptance Criteria

| # | User Story | Acceptance Criteria |
|---:|---|---|
| 1 | As a student, I want to ask natural-language questions about university policies and procedures so that I can obtain accurate, source-grounded information without manually searching university documents. | Given a question answerable from the corpus, the system returns a correct answer with at least one cited source document. Response time is reported. |
| 2 | As a student, I want the system to tell me when it cannot provide a grounded answer so that I am not misled by an unsupported or fabricated response. | Given a question outside the corpus, the system explicitly states it cannot find a grounded answer and suggests contacting support/staff, rather than generating an unsupported answer. |
| 3 | As a student, I want to check my exam timetable through the | Given a valid (synthetic) student identifier and course, the system retrieves and correctly displays the matching timetable entry from the sample data store. |
| 4 | As a student, I want to check the status of a support case I previously raised so that I can know whether my issue is being handled. | Given a valid case ID, the system returns the correct current status (e.g., "open," "in progress," "resolved") from the case-status store. |
| 5 | As a student, I want to raise a support ticket directly through the conversation when my issue cannot be resolved using the available information so that I do not need to use a separate system. | Given an unresolved/unanswerable query, the system drafts a ticket (issue summary, category, student reference) and creates it via the ticket tool; the created ticket ID is returned to the student. |
| 6 | As a student, I want the assistant to remember the support case I am discussing during my conversation so that I do not have to repeat the case ID in every message. | After a ticket is created or looked up, subsequent messages in the same session that refer to "my case"/"it" correctly resolve to the same case ID without the student restating it. |
| 7 | As a student, I want to be clearly told when my request requires human review so that the system does not make decisions that should be handled by university staff. | Given a request touching admissions, grading, discipline, or fees, the system declines to act, explains that this requires human review, and (where applicable) creates a ticket routed to the appropriate human staff category. |
| 8 | As a support staff member, I want every ticket created by the agent to contain sufficient context so that I can understand the student's issue without unnecessarily asking the student to repeat the information. | Every system-created ticket contains: student reference, category, question/issue text, any retrieved evidence used, and timestamp. |
| 9 | As a support staff member or project team member, I want to see why the system produced an answer or performed an action so that its behaviour can be inspected and audited. | For any grounded answer, the underlying retrieved source(s) and, for any tool call, the tool name/inputs/outputs are available in a trace/log. |
| 10 | As a project team member, I want the agent to operate within a defined limit on iterations and tool calls so that it cannot loop indefinitely or perform unbounded actions. | The agent workflow enforces a maximum iteration/tool-call count per user turn; exceeding it causes a safe stop and a message to the user rather than a silent failure or infinite loop. |
| 11 | As a student, I want to ask follow-up questions about the same topic without repeating the previous context so that the interaction remains natural and useful. | Given a follow-up question that depends on the prior turn (e.g., "what about for second-years?"), the system correctly uses session state to interpret it in context. |
| 12 | As a project team member, I want a controlled evaluation set of scenarios so that I can measure whether the system behaves correctly, reliably, and safely before the final demonstration. | A documented set of ≥30 scenarios (normal, edge, unanswerable, adversarial, out-of-boundary) exists with expected vs. actual results recorded by Week 7. |
